# API de Deriv — Native API vs MT5, para el `DerivDemoAdapter` (Fase 3, paso 2)

Estado: investigación hecha, pendiente aprobación de Moisés antes de implementar `DerivDemoAdapter`. Modo: 100% PAPER (cuenta Deriv-Demo). Nada de dinero real.
Detalle (tabla de endpoints, scopes, secuencia WS): `01_DETALLE_API_DERIV.md`. MT5 para cuentas de FONDEO (prop firms, distinto del CFD propio de Deriv): `02_DETALLE_FONDEOS_MT5_MULTICUENTA.md` (investigación 2026-07-07).

## 0. Matiz importante (2026-07-07): esta decisión aplica al CFD propio de Deriv, NO a fondeos
La recomendación de este documento ("Native API, no MT5") es correcta para el trading CFD directo de Moisés en Deriv. **No aplica a cuentas de fondeo (prop firms)**: casi ninguna prop firm ofrece una API pública equivalente a la Native API de Deriv — entregan una cuenta MT4/MT5 y el trader debe operar ese terminal. Para fondeos, ver `02_DETALLE_FONDEOS_MT5_MULTICUENTA.md`: el único producto oficial de MetaQuotes para multi-cuenta (MAMM/PAMM) es para brókeres/gestores licenciados, no para un trader retail operando sus propias cuentas fondeadas — automatizar ahí exige un EA local (MQL5) por terminal + un puente hacia el motor central, en una VPS Windows dedicada.

## 1. Native API (WebSocket) vs acceso vía MT5 — RECOMENDACIÓN: Native API (para el CFD propio de Deriv)
Deriv ofrece dos vías distintas: la **Deriv API** (WebSocket JSON puro, `developers.deriv.com`, pensada para que desarrolladores construyan apps propias en cualquier lenguaje/OS) y **Deriv MT5** (terminal MetaTrader 5, requiere EA en MQL5 y un terminal Windows corriendo 24/7; Deriv confirma oficialmente que **no ofrece VPS propio** para MT5 — el usuario debe montar su propio VPS). Para un motor automatizado en modo paper, la Native API es la opción correcta: sin terminal Windows, integrable directamente en el monolito Node/TypeScript, coherente con la nota ya registrada en `00_FOUNDATION/03` de que MT5 exige infraestructura Windows aparte (bloqueada hasta que se justifique). MT5 solo se reconsidera si en el futuro se necesita un símbolo/mercado que la Native API no cubra, **o si se escala a cuentas de fondeo** (ver §0), donde SÍ está justificado.

## 2. Autenticación — scope mínimo: `read` + `trade`
Modelo: `app_id` (registrado una vez en el dashboard de Deriv, identifica la aplicación) + **token de API** (Personal Access Token, generado por Moisés en su cuenta Deriv: Security & Limits → API token) o alternativamente OAuth 2.0 (pensado para apps multi-usuario; no aplica aquí, 1 sola cuenta demo). Scopes disponibles: `read` (lectura de datos de cliente), `trade` (crear/cerrar contratos), `trading_information` (leer historial de operaciones), `payments` (cashier: depósitos/retiros), `admin` (cambiar configuración de cuenta). **Mínimo necesario para paper trading: `read` + `trade`** — cubre balance, cotizaciones autorizadas, envío/cierre de contratos y portfolio. `payments` y `admin` quedan explícitamente EXCLUIDOS del token (menor privilegio, coherente con `18_SECURITY`). El token vive en `DERIV_API_TOKEN` (env var, ya en `.env.local`), nunca en código/chat/docs — Claude no lo maneja, solo documenta su uso. Para N cuentas propias (fan-out, ver `14_PORTFOLIOS/02_DETALLE_FANOUT_MULTICUENTA.md`): un token distinto por cuenta, mismo `app_id` (es por aplicación, no por cuenta).

## 3. WebSocket persistente — Vercel serverless vs proceso propio: RESUELTO → proceso propio en el VPS Hetzner
La conexión a Deriv es `wss://ws.derivws.com/websockets/v3?app_id={app_id}`, con **timeout de inactividad de 2 minutos** (requiere ping/time periódicos) y **sin reanudación de sesión tras desconexión** — cada reconexión exige un WebSocket nuevo, re-`authorize` y re-suscribir todo desde cero. Documentación oficial de Vercel (`vercel.com/docs/functions/limitations`, consultada 2026-07) confirma que las Functions con Fluid Compute tienen **duración máxima 300s (Hobby) / 800s estándar / 1800s extendido-beta (Pro-Enterprise)** — tras ese tiempo la función se termina — y que aunque soportan handshakes WebSocket, "future connections are not guaranteed to connect to the same Function", es decir, no hay pin de sesión garantizado entre reconexiones. Un cliente que debe mantenerse autenticado y suscrito 24/7 con reconexión con estado propio (posiciones abiertas, listeners activos) **no encaja en ese modelo**. **Recomendación: el motor de trading (cliente WebSocket a Deriv) corre como proceso Node.js propio de larga duración en el VPS Hetzner ya existente** (reutiliza infra, coherente con la señal de extracción ya anotada en `02_ARCHITECTURE/00_RESUMEN.md`), NO como Vercel Function. El dashboard/API del SaaS (Next.js en Vercel) sigue siendo serverless y solo lee resultados (vía Supabase), sin abrir WebSocket a Deriv directamente.
**Sin confirmar explícitamente por Vercel**: no existe una declaración oficial que diga "no uses Vercel Functions para un cliente WebSocket de trading 24/7"; la conclusión anterior es una inferencia razonada a partir de los límites de duración documentados + comportamiento de Deriv (sesión no reanudable), no una prohibición literal. Se marca como la recomendación más prudente, no como hecho confirmado al 100%.

## 4. Endpoints clave del ciclo de vida de una orden (ver tabla completa en el detalle)
`authorize` (token) → `balance` (cuenta/saldo, incl. `is_virtual`) → `ticks`/`ticks_history` (precios, públicos) → `proposal` (cotización de contrato, público) → `buy` (ejecutar, requiere `proposal_id`, scope `trade`) → `portfolio` (posiciones abiertas) → `sell` (cerrar contrato, scope `trade`) → `forget_all` + cierre de socket (desconectar). `website_status` expone `call_limits`/`api_call_limits` para consultar los rate limits vigentes de forma programática — **Deriv no publica cifras fijas de rate limit**; deben consultarse en runtime, no asumirse. Exceder el límite devuelve error (no ban automático), pero abuso sostenido puede suspender la app — mapear como fallo del broker al circuit breaker de `09_RISK` (regla 5c).

## 5. Mapeo a `BrokerAdapter` (interfaz ya definida en `08_TRADING/01_DETALLE_ADAPTADOR_Y_CICLO_DE_VIDA.md`)
`conectar` → abrir WS con `app_id` · `autenticar` → `authorize(token)` · `obtener_cotizacion` → `ticks`/`proposal` · `obtener_cuenta` → `balance` (+ datos de `authorize`) · `enviar_orden` → `proposal` + `buy` · `obtener_posiciones` → `portfolio` · `cancelar_orden` → `sell` (Deriv no tiene "cancelar antes del fill": los contratos se compran al instante contra una `proposal`, así que "cancelar" en la práctica es cerrar/`sell` una posición ya abierta — matiz frente a un forex tradicional) · `desconectar` → `forget_all` + cierre del socket.

## 6. Riesgos/gotchas
- Timeout de inactividad de 2 min → requiere heartbeat explícito (`ping`/`time`).
- Reconexión = sesión nueva: el motor debe re-sincronizar balance/posiciones tras cada reconexión, nunca asumir continuidad de estado.
- Cuenta demo: resettable a $10,000 USD sin límite de veces vía API/UI; si el comportamiento de fills/spreads es 100% idéntico a la cuenta real: **sin confirmar** (heredado de `08_TRADING`).
- Rate limits dinámicos y no publicados como cifra fija — depende de `website_status` en cada sesión.
- `app_id` es por aplicación, no por usuario; con un solo PAT de la cuenta demo de Moisés es suficiente para este paso (no se necesita OAuth multi-usuario todavía).
